## Бизнес-постановка

Банк хочет автоматически выявлять мошеннические операции по банковским картам в момент авторизации. Если модель считает транзакцию подозрительной, её можно заблокировать или направить на дополнительную проверку: отправить клиенту SMS, позвонить ему или передать операцию в службу безопасности.

Цель бизнеса - уменьшить финансовые потери от мошенничества. При этом важно не блокировать слишком много легитимных операций: это создаёт неудобства клиентам и увеличивает нагрузку на службу поддержки. Поэтому система должна находить баланс между полнотой выявления мошенничества и количеством ложных тревог.

## Постановка ML-задачи

Это задача **бинарной классификации**. Объект - банковская транзакция. Целевая переменная - `Class`:
- `0` - легитимная транзакция;
- `1` - мошенническая транзакция.

Модель получает признаки транзакции и предсказывает вероятность того, что она мошенническая. Затем выбирается порог вероятности: транзакции с вероятностью выше порога помечаются как подозрительные. Порог подбирается исходя из бизнес-ограничений - допустимого количества ложных блокировок и стоимости ручной проверки.

## Данные

Используется открытый датасет [Credit Card Fraud Detection (ULB, Kaggle)](https://www.kaggle.com/datasets/mlg-ulb/creditcardfraud). Он содержит 284 807 транзакций европейских держателей карт за два дня сентября 2013 года, из которых 492 являются мошенническими, то есть примерно 0,172% выборки.

| Признак    | Описание                                                                                     |
| ---------- | -------------------------------------------------------------------------------------------- |
| `V1`-`V28` | Анонимизированные числовые признаки, полученные с помощью PCA для защиты персональных данных |
| `Time`     | Количество секунд, прошедших с первой транзакции в датасете                                  |
| `Amount`   | Сумма транзакции                                                                             |

Датасет достаточен для решения задачи: в нём почти 285 тысяч наблюдений и 492 положительных примера, а признаки уже числовые и пригодны для обучения моделей машинного обучения.

## Выбор и обоснование метрики

**Основная метрика - AUPRC (Area Under Precision-Recall Curve, PR-AUC).**
При таком сильном дисбалансе классов accuracy неинформативна: модель, которая всегда предсказывает «легитимная транзакция», получит accuracy около 99,8%, но не найдёт ни одного мошенника. AUPRC оценивает качество именно на редком положительном классе и не зависит от большого количества истинно отрицательных примеров. Precision и recall также подходят для несбалансированных выборок, поскольку, в отличие от accuracy, не зависят от соотношения классов.

**Дополнительные метрики:**
- **Recall при фиксированном Precision** - например, «поймать не менее 80% мошеннических операций при precision не ниже 80%». Recall показывает долю найденных мошеннических операций, а precision - долю действительно мошеннических среди операций, которые модель пометила как подозрительные.
- **Бизнес-метрика:** сумма предотвращённых потерь по мошенническим транзакциям минус стоимость ложных блокировок и ручных проверок. Она позволяет выбрать порог классификации с учётом реальной цены ошибок.

Использование AUPRC и пары precision/recall соответствует бизнес-логике задачи: банк хочет не просто хорошо классифицировать все транзакции, а именно находить редкие мошеннические операции, не создавая чрезмерного числа ложных тревог.

## Выводы по EDA и план дальнейшей работы

По результатам разведочного анализа можно сделать следующие выводы:
- Датасет имеет экстремальный дисбаланс классов: мошеннические транзакции составляют около 0,17% выборки.
- Accuracy не подходит для оценки качества модели; основной метрикой выбрана AUPRC, а дополнительными - precision и recall.
- Признак `Amount` имеет скошенное распределение, поэтому для некоторых моделей целесообразно использовать `log1p(Amount)` и `RobustScaler`.
- Из `Time` можно извлечь признак `Hour`, который может отражать суточные паттерны мошенничества.
- Признаки `V1`-`V28` почти не коррелируют между собой, так как получены методом PCA.
- Выбросы не следует удалять автоматически, поскольку они могут быть важным сигналом мошенничества.
- Для обучения стоит использовать стратифицированную или временную валидацию, а балансировку классов применять только внутри обучающей выборки.

**План предобработки и моделирования:**
1. Удалить дубликаты, если они обнаружены.
2. Создать признак `Hour` из `Time`.
3. Преобразовать `Amount` с помощью `log1p` и при необходимости масштабировать признаки.
4. Разделить данные на train и test с учётом времени или с использованием стратификации.
5. Обучить baseline-модель, например логистическую регрессию.
6. Обучить более сложные модели: Random Forest, LightGBM или CatBoost.
7. Подобрать порог классификации по AUPRC, precision/recall и бизнес-метрике.
8. Оценить итоговую модель на отложенной тестовой выборке.
